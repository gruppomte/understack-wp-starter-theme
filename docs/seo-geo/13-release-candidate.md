## 3. Final architecture

`app/Seo` (namespace `Understack\Seo`, one `Registrable` service in `Theme::SERVICES`):

- Core: `Seo` (boot, lazy per-request state), `Config` (defaults ← `config/seo.php` ← filter, validated), `Provider` (detection by version constant), `Signal` / `Owner` / `Ownership` (who emits what), `PageKind` / `PageContext` (the request), `Text` (plain-text helpers).
- Output: `Meta\Head` (one `wp_head` callback: description, canonical, social tags, JSON-LD), `Meta\Description`, `Meta\Canonical` (listings; comment-page correction on singular), `Meta\Social`; `Indexability\Environment` / `Verdict` / `Policy` (robots directives through `wp_robots`, `rank_math/frontend/robots` and `wp_headers`); `Sitemap` (core sitemap filters); `Crawlers\Groups` / `Policy` (robots.txt groups from configuration); `Breadcrumbs` + `views/partials/breadcrumbs.twig` (Twig function `breadcrumbs()`).
- Entities: `Identity\Identity` (validated value object), `Identity\Types` (176 verified Schema.org types), `Identity\Repository` (options read with one primed query, filterable); `StructuredData\Input` / `Collector` / `Graph` / `Serializer` / `Author`.
- Compatibility: `Integrations\Wpml` (page id mapping through `wpml_object_id`), `Integrations\WooCommerce` (allowances per page role).
- Diagnostics: `Diagnostics\Checks` / `Status` (pure rules), `Report`, `SiteHealth`, `Command` (`wp <slug> seo report`, exit 1 on FAIL).

Principles kept throughout: WordPress core first, the SEO plugin owns its signals, the theme is the fallback; no vendor token in the runtime; no admin screens; no external requests; no persistent cache of its own; everything white-label.

## 7. Performance audit

Method: local site (WordPress 7.1.3, PHP 8.5.3, MySQL, no page cache, no persistent object cache, `WP_ENVIRONMENT_TYPE=local`), a temporary must-use probe (`tests/perf/probe.php`) that records per request the total time, database queries (with duplicates through `SAVEQUERIES`), peak memory, hooks registered by the SEO module, time of the theme's head output, time to build the JSON-LD graph (average of five builds) and HTTP API requests; `tests/perf/measure.mjs` takes 10 samples per path after two warm-ups and reports median (min–max). Baseline: a `git worktree` of `v2027.1` with the same compiled assets and production dependencies, activated as a second theme. Rounds alternated baseline / current to expose drift; the sample identity (with address and profiles) was configured for the current theme in rounds 1–2 and removed for round 3. Variability between rounds: medians within 1.5 ms; query counts and bytes identical across rounds.

| ---------------------------- | ---------------- | --------------- | ------------------------------- | -------------------------------------------- | -------------------------- | ---------- | --------------------------------- | ----------------------------- |
| `/`                          | 28               | 31              | 19.4 / 19.7                     | 22.4 / 20.6 / 21.1                           | 0.04 → 0.28                | 0.02–0.03  | 7147 → 7354                       | 26,828 → 28,105               |

Findings:

- Before this increment the foundation added 14 queries per page: every unset identity option read through ACF cost a query (WordPress caches missing options only within a request without a persistent object cache). Fixed in `259a4fa`: `Identity\Repository` reads the options directly and primes them with one `wp_prime_option_caches()` call (a second one for repeater rows); ACF is no longer called at runtime.
- After the fix the theme adds one query (the prime). The other two of the +3 above are WordPress core lookups of the user global styles post and the `wp_theme` term for the active theme folder (the baseline folder had never been opened in the editor, so its lookups return nothing); they are not attributable to the SEO code.
- Duplicate queries: 0 in every state. Hooks registered by the module: 12. Bootstrap: 0.03 ms. Head output: +0.25 to +0.35 ms. JSON-LD: 0.02–0.09 ms. Peak memory: about +200 KB. HTML: +1.3 KB on listings, +2.9 KB on a post (social tags and graph). HTTP requests: 0. Total time: +1 to +3 ms per page on this machine, within the inter-round variability of the baseline itself.
- Caching: output is deterministic per URL (no cookies, nonces or user data), so page caches serve it as any other page; with a persistent object cache the prime query disappears after the first request; no transient or cache of its own was introduced.
- Not measured: front-end metrics (LCP, INP, CLS) — the increment adds no CSS or JavaScript and the only markup change is the breadcrumb trail when enabled; Lighthouse was not run and is not claimed.

## 9. Known limitations

- WPML: designed and mock-tested, not certified; the list of tests that need a real installation is in `07-compatibility.md`.
- SEO plugins other than Rank Math and Yoast: detection only.
- CI runs the end-to-end suite without SEO plugins and without WooCommerce; those combinations are local verifications with committed reports.
- The crawler policy governs the virtual robots.txt only; the diagnostics mark everything outside the theme as NOT VERIFIED.
- Accessibility checks cover the elements the foundation touches or relies on; this is not a full WCAG 2.2 audit of the theme.
- HTML validation used a temporary tool (`npx html-validate`), not part of the repository.
- The performance numbers come from one local machine; absolute values vary, the relative cost (one query, under half a millisecond of head output, a few kilobytes) is the finding.
